# CorpusLens : Alpaca-GPT4 Corpus Audit & Quality Engineering Pipeline

Auditing a 52k row instruction-tuning corpus to answer a question fine-tuning teams rarely ask before spending GPU budget: **is this training data actually good enough to train on?**

`Python` · `pandas` · `scikit-learn` · `sentence-transformers` · `MySQL` 

---

## The problem

A team fine-tuning an open-source assistant plans to train on **alpaca-gpt4**, a widely-used 52K-row instruction corpus. It is *synthetic* — the instructions were auto-generated from a small seed set and the responses were generated by GPT-4. No human reviewed any of it.

Synthetic generation has known, predictable failure modes:

- **Redundancy** — the generator loops back to near-identical phrasings
- **Task skew** — easy, verbose task types are over-produced; hard ones under-produced
- **Degenerate outputs** — truncations, stunted answers, repetition loops

Training on unaudited data means paying compute to teach a model its predecessor's mistakes. This project quantifies all three failure modes and returns a prioritised list of corpus actions.

**Three questions, and where each is answered:**

| # | Question | Method | Output |
|---|---|---|---|
| Q1 | Is the corpus balanced across task types? | Embedding clustering | `v_cluster_composition`, `v_rule_vs_cluster` |
| Q2 | How much of it is redundant? | TF-IDF cosine similarity | `v_duplicate_rate`, `v_duplicate_pairs` |
| Q3 | Which responses are low quality? | Composite flag scoring | `v_worst_by_cluster`, `v_flag_prevalence` |

---

## Dataset

**`vicgalle/alpaca-gpt4`** — 52,002 rows.

| Column | Description |
|---|---|
| `instruction` | The task given to the model |
| `input` | Optional extra context (empty in roughly 60% of rows) |
| `output` | GPT-4's response |
| `text` | The three concatenated for training — dropped during cleaning |

One row is one isolated task. **There are no users, sessions, timestamps, or follow-up turns.** Every finding in this project is therefore a statement about the *corpus*, never about human behaviour.

## Methodology

### Stage 1 — Clean and enrich

Cleaning happens once, up front, before any feature derives from the text. Rows with empty instruction or output are dropped; exact duplicate `instruction + input` pairs are flagged.

Features engineered: word counts, sentence count, words-per-sentence, Flesch reading ease, readability band, and a baseline rule-based task classifier.

**Two decisions worth defending:**

*Sentence count floors at 1.* An output with no terminal punctuation really is one run-on sentence. Returning 0 would make `words_per_sentence` infinite and poison every downstream distribution.

*Flesch is only scored on prose.* Code blocks and tables return large negative Flesch values that are meaningless and would dominate every readability cut. Outputs matching 2+ code markers are flagged `is_code_like` and left unscored rather than silently mis-scored.

### Stage 2 — Clustering

The rule-based classifier matches on leading verb only, so indirectly-phrased instructions fall into `Other`. **That `Other` rate is the headline number motivating this stage** — it is reported in full, not sliced away.

Instructions are embedded with `all-MiniLM-L6-v2`. `k` is selected by a silhouette sweep across 5–12 and the scores are written to `outputs/cluster_selection.json` so the choice is auditable rather than asserted. K-Means is fit on a 15K sample; the remaining rows are assigned to the nearest centroid.

Each cluster is then **named by hand** after reading its ten closest-to-centroid instructions. An unnamed cluster is a number; a named cluster is a finding.

### Stage 3 — Duplicates and quality

**Near-duplicates.** TF-IDF (1–2 grams) → cosine nearest-neighbour, threshold **0.90**, computed *within* each cluster. Two reasons: near-duplicates are semantically similar and land in the same cluster anyway, and it turns one 52K×52K problem into a dozen tractable ones. Only the later row of a pair is flagged, so dropping all flagged rows always leaves one copy behind.

The 0.90 threshold is deliberately conservative — it catches near-verbatim restatements without flagging instructions that merely share a template.

**Quality flags.** Five booleans:

| Flag | Rule |
|---|---|
| `flag_truncated` | Output doesn't end on terminal punctuation |
| `flag_too_short` | Under 15 words |
| `flag_empty_ish` | Under 3 words |
| `flag_repetitive` | Same 5-gram appears 3+ times (generator loop) |
| `flag_readability_outlier` | Flesch outside its own cluster's 1.5×IQR range |

Outliers are judged **within cluster** because a code-explanation cluster legitimately reads harder than a creative-writing one.

`adequacy_score = 100 − (n_flags × 20)`, floored at 0.

**Validation.** 20 low-adequacy rows are exported to `outputs/manual_review_sample.csv` for manual reading. *An unvalidated score is an assertion* — record the hit rate below before presenting any of this.

### Stage 4 — MySQL

Schema is hand-written in `sql/01_schema.sql`, not inferred by pandas. `to_sql` guessing gives TEXT columns for integers and a utf8mb3 default that mangles unicode in GPT-4 outputs. Indexes on `cluster_id`, `adequacy_score`, and `output_word_count` exist because the window-function views partition and sort on them.

The nine views in `sql/02_views.sql` use `SUM() OVER ()`, `RANK() PARTITION BY`, `NTILE(4)`, `PERCENT_RANK()`, `AVG() OVER (PARTITION BY)`, a CTE, and a subquery-wrapped window filter. Requires MySQL 8.0+.

## Running it

```bash
git clone <repo> && cd llm-corpus-audit
pip install -r requirements.txt

# full pipeline, database load skipped
python src/run_all.py --skip-mysql

# fast smoke test on 2,000 rows
python src/run_all.py --limit 2000 --skip-mysql
```

To include the database layer:

```bash
mysql -u root -p < sql/01_schema.sql     # create schema
# set credentials in src/config.py
python src/run_all.py                     # runs stages 1-4
mysql -u root -p corpus_audit < sql/02_views.sql
```

Then point Power BI at `corpus_audit` and import the nine `v_*` views.

**Stage-by-stage** if you'd rather run it piecewise:

```bash
python src/stage1_clean_enrich.py
python src/stage2_clustering.py    
python src/stage3_quality.py
python src/stage4_load_mysql.py
```

Every threshold that affects a finding lives in `src/config.py`, not buried in the code.

## Limitations

**Corpus claims only.** This dataset has no user or session identifiers. Nothing here says anything about how people prompt, what they prefer, or where they struggle. Claims stay at the corpus level throughout.

**No measured model improvement.** The recommendation is *which rows to drop*. Whether dropping them improves a fine-tuned model is untested — that would require training and evaluating two models, which is out of scope. The project claims a corpus action, not an accuracy delta.

**Thresholds are heuristic.** 0.90 cosine, 15 words, 5-gram×3 — all defensible, none canonical. They are centralised in `config.py` specifically so a reviewer can change them and re-run.

**Flesch on non-prose is excluded, not solved.** Code-like outputs are left unscored. A more complete treatment would use a separate complexity metric for code.

**Clustering is fit on a sample.** K-Means is fit on 15K of 52K rows for tractability; the rest are assigned by nearest centroid. Cluster boundaries would shift slightly under a full fit.
